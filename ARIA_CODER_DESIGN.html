Section 05 — Tiered Autonomy Model
05
Section 05
What ARIA Decides vs What Needs Approval
Tier 1 — Full Auto
Silent execution + notification

Bug fixes in existing modules — exceptions, parse failures, timeouts

Content additions — new knowledge facts, source URLs, RSS feeds

Performance — caching, dedup, timeout adjustments

Test additions — new regression tests for known gaps

Config tweaks — env var defaults, log levels, intervals

Deploys silently → WhatsApp after

Tier 2 — WA Approval
Operator approve before deploy

New modules — new DD layer, new API endpoint, new source integrator

Dependency additions — new Python package or npm module

Schema changes — new Redis key patterns, ChromaDB collections

External integrations — new third-party API wiring

Hallucination guard changes — any modification near guard logic

WhatsApp request → wait up to 30min → deploy on confirm

Tier 3 — Hard Gate
Human + operator, always

Constitution — any change to the 25 clauses

Security boundaries — auth, JWT, API key handling

Billing — Stripe, GPU rental, RunPod

Architecture — new Fly.io apps, volume resizing

Self-modification of constitutional_validator.py or fly_deployer.py

Never autonomous — requires code review

Clause 26 — The Meta-Constitutional Rule: Before writing any code that modifies ARIA's own inference pipeline, hallucination guards, or constitutional enforcement, ARIA must pause, present the proposed change to the operator via WhatsApp, and wait for explicit confirmation. Self-improvement that weakens safety constraints is categorically forbidden regardless of apparent benefit. This clause governs the rule-writer — it cannot itself be modified autonomously.

The Seven Non-Negotiable Properties
Property 1
Constitutional by design

Every piece of code ARIA generates passes through ConstitutionalValidator before testing. AST-level checks, not just linting. The validator cannot be modified autonomously. This is the load-bearing safety property.

Property 2
Sovereign by default

ARIA-LLM is the primary model for all coding tasks. DeepSeek and Anthropic are fallbacks, not defaults. Every session that uses a sovereign model costs £0 in API fees. The goal is 90%+ sovereign by Month 6.

Property 3
Auditable at every step

Every autonomous action writes to the HMAC audit log. Every R-number is traceable to the specific gap that generated it. Every deployed commit is signed. Legal defensibility requires this.

Property 4
Test-isolated always

Production code is never modified during testing. aria-runner spins ephemeral Fly.io machines per test run, destroyed after. Code reaches production only after 100% test pass and canary smoke test.

Property 5
Rollback instant

Every deployment stores its image digest in Redis. Rollback is one command. The 30-minute post-deploy monitoring window auto-triggers rollback on regression. No deployment is permanent until monitoring clears.

Property 6
Compounding training data

Every quality output ARIA produces — DD reports, compliance opinions, autonomous fixes — becomes a training pair via output_harvester. DPO pairs come from adversarial failures. The fine-tune improves with every operational day.

Property 7
WhatsApp-native operation

Every operator interaction — DD requests, fix approvals, status queries, cost checks — works entirely through WhatsApp. No dashboard required for daily operations. ARIA sends autonomous daily briefings, gap alerts, and deployment confirmations without being asked.

The honest ceiling
100% is asymptotic, not a destination

No LLM can achieve zero hallucinations. The six-layer defence-in-depth architecture (prompt constitution → in-flight validation → output rewrite → multi-provider consensus → post-hoc audit → adversarial regression) brings ARIA asymptotically close. After Phase E, hallucinations on ARIA's known domains should be <1%. Unknown domains remain higher — which is why the citation-first discipline and UNVERIFIED/ASSESSED confidence tags exist.
